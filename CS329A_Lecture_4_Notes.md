# CS329A --- Lecture 4: Feedback Loops, Tool Use, and Self-Improvement

## 0. Lecture Overview

### Central theme

Lecture 4 studies how AI systems can improve their behavior by **acting,
receiving feedback, and adapting**.

The lecture connects three papers that use different feedback sources:

1.  **ReAct** --- feedback from interacting with an external
    environment/tools.
2.  **RLEF** --- feedback from executing generated code.
3.  **Constitutional AI** --- feedback generated by an AI evaluator
    guided by human-written principles.

The common abstraction is:

\[ x_t `\rightarrow `{=tex}y_t `\rightarrow `{=tex}F(y_t)
`\rightarrow `{=tex}`\text{feedback}`{=tex} `\rightarrow `{=tex}x\_{t+1}
\]

The central research question is not simply whether feedback helps, but:

> **How informative, reliable, cheap, and scalable is the feedback?**

# 2. ReAct

## 2.1 Core idea

**ReAct = Reason + Act**

Instead of requiring the model to reason entirely internally, ReAct
interleaves reasoning with actions in an environment.

Basic loop:

\[ `\boxed{
\text{Thought}
\rightarrow
\text{Action}
\rightarrow
\text{Observation}
\rightarrow
\text{Thought}
\rightarrow \cdots
}`{=tex} \]

Example:

``` text
Question
   ↓
Reason
   ↓
Search / tool call
   ↓
Observe result
   ↓
Reason using new information
   ↓
Another action if needed
   ↓
Final answer
```

The key difference from reasoning alone is that **the environment
provides new information**.

------------------------------------------------------------------------

## 2.2 Why reasoning alone can be insufficient

An LLM's parameters contain learned knowledge, but they do not
automatically provide live information.

For questions such as:

-   current prices,
-   current events,
-   external database state,
-   information not contained in the model,

the model may need to interact with an external source.

The environment therefore becomes part of the reasoning loop.

Instead of:

\[ `\text{Model}`{=tex} `\rightarrow `{=tex}`\text{Answer}`{=tex} \]

we have:

\[ `\text{Model}`{=tex} `\rightarrow`{=tex} `\text{Action}`{=tex}
`\rightarrow`{=tex} `\text{Environment}`{=tex} `\rightarrow`{=tex}
`\text{Observation}`{=tex} `\rightarrow`{=tex} `\text{Model}`{=tex} \]

The observation becomes part of the next reasoning state.

------------------------------------------------------------------------

## 2.3 ReAct examples

ReAct can be applied to tasks involving:

-   question answering,
-   fact verification,
-   web interaction,
-   shopping,
-   external APIs,
-   other environments where actions produce observations.

The lecture discusses applications such as:

-   **HotpotQA**
-   **FEVER**
-   **WebShop**

------------------------------------------------------------------------

# 3. ReAct: Action Space

An agent must decide **which action to take next**.

If there are (A) possible actions and the agent acts for (T) steps, the
naive number of possible action sequences can grow approximately as:

\[ A\^T \]

This creates an action-space problem.

More tools do not automatically make an agent better.

A large action space can lead to:

-   unnecessary tool calls,
-   wandering/search loops,
-   increased latency,
-   increased token usage,
-   error propagation,
-   difficulty deciding which tool is appropriate.

------------------------------------------------------------------------

# 4. Why Unlimited Tool Calls Are Not Automatically Better

Unlimited tool use introduces several costs.

## 4.1 Compute and latency

If every tool call has cost (C\_{`\text{tool}`{=tex}}):

\[ C\_{`\text{total}`{=tex}} = C\_{`\text{reasoning}`{=tex}} +
N\_{`\text{tools}`{=tex}}C\_{`\text{tool}`{=tex}} \]

Increasing the number of tool calls indefinitely is expensive.

## 4.2 Error accumulation

A tool can return:

-   incorrect information,
-   incomplete information,
-   noisy information,
-   unexpected results.

The model can then reason correctly from an incorrect observation.

## 4.3 Action-space explosion

More tools create more possible action sequences.

Therefore, the important question becomes:

> **When should an agent reason internally, and when should it interact
> with the environment?**

------------------------------------------------------------------------

# 5. Reasoning vs Action Allocation

An agent has a limited inference budget.

For example:

``` text
90% reasoning + 10% tool calls
```

versus:

``` text
50% reasoning + 50% tool calls
```

versus:

``` text
10% reasoning + 90% tool calls
```

There is no universally optimal ratio.

Different tasks require different allocations.

### Examples

  Task                          Potentially useful behavior
  ----------------------------- -------------------------------------
  Current factual information   Tool call
  Mathematical derivation       More internal reasoning
  Programming                   Reason → execute → observe → repair
  External research             Reason → search → observe → reason
  Stalled reasoning             Critic or additional feedback

This motivates **adaptive reasoning/action allocation** as a research
direction.

------------------------------------------------------------------------

# 6. RLEF --- Reinforcement Learning from Execution Feedback

## 6.1 Core idea

Code generation provides an unusually useful environment:

> **Generated code can actually be executed.**

Instead of asking another model whether the code looks correct, we can
execute it and observe what happens.

Basic loop:

\[ `\boxed{
\text{Generate code}
\rightarrow
\text{Execute}
\rightarrow
\text{Observe feedback}
\rightarrow
\text{Repair}
\rightarrow
\text{Execute}
\rightarrow \cdots
}`{=tex} \]

------------------------------------------------------------------------

# 7. RLEF as an RL Problem

A coding task can be represented as an RL-style interaction.

### State

The state can include:

\[ s_t =
(`\text{problem}`{=tex},`\text{current code}`{=tex},`\text{feedback/history}`{=tex})
\]

### Action

The model generates or modifies code:

\[ a_t = `\text{code generation/modification}`{=tex} \]

### Environment

The execution environment runs the code.

### Observation

The environment can return:

``` text
PASS
```

or:

``` text
FAIL
Expected: 10
Got: 7
```

### Reward

A simple reward can be:

\[ r_t =
```{=tex}
\begin{cases}
1 & \text{tests pass}\\
0 & \text{tests fail}
\end{cases}
```
\]

The exact implementation can vary, but the important concept is that
**execution provides grounded feedback**.

------------------------------------------------------------------------

# 8. Why Execution Feedback Is Powerful

Compare:

### SFT-style behavior

\[ `\text{Problem}`{=tex}
`\rightarrow `{=tex}`\text{Correct Code}`{=tex} \]

with:

### Feedback-driven behavior

\[ `\text{Problem}`{=tex} `\rightarrow`{=tex} `\text{Code}`{=tex}
`\rightarrow`{=tex} `\text{Execution}`{=tex} `\rightarrow`{=tex}
`\text{Failure}`{=tex} `\rightarrow`{=tex} `\text{Repair}`{=tex} \]

The second setup teaches the system to condition its next behavior on
**observed outcomes**.

This can make the model better at repairing mistakes rather than simply
reproducing patterns seen during training.

Important nuance:

> RLEF does not necessarily mean the model has tried every possible
> solution. Its key advantage is that its next action can depend on
> concrete feedback from previous attempts.

------------------------------------------------------------------------

# 9. Two-Tier Testing

A useful setup separates tests used during iterative solving from tests
used for final evaluation.

### Public tests

Used to provide iterative feedback:

``` text
Generate
→ run public tests
→ observe
→ repair
```

### Private tests

Used for final evaluation.

This prevents the model from simply optimizing directly against the
complete evaluation set.

------------------------------------------------------------------------

# 10. Limitations of Binary Execution Feedback

A simple reward:

\[ r `\in `{=tex}{0,1} \]

contains very little information.

Consider:

### Program A

``` text
10/10 tests pass
```

### Program B

``` text
1/10 tests pass
```

Both may receive:

\[ r=0 \]

if one hidden test still fails.

The reward therefore does not distinguish how close the solutions are.

A richer signal could be:

\[ r = `\frac{\text{tests passed}}{\text{tests attempted}}`{=tex} \]

giving:

\[ r_A=0.9 \]

\[ r_B=0.1 \]

But even this is imperfect because all tests may not have equal
importance.

------------------------------------------------------------------------

# 11. Feedback Granularity

Execution feedback can exist at different levels:

``` text
Binary
PASS / FAIL
        ↓
Test-level
9 / 10 tests passed
        ↓
Error-level
IndexError on line 27
        ↓
Trace-level
Execution path + failure information
        ↓
Step-level
Which generation/decision caused the failure
```

More detailed feedback is not automatically better.

Detailed feedback may be:

-   expensive,
-   noisy,
-   difficult to interpret,
-   computationally expensive,
-   misleading.

Therefore, a research question is:

> **What is the optimal granularity of execution feedback?**

------------------------------------------------------------------------

# 12. Adaptive Feedback Granularity

A useful research idea is to avoid always using the most expensive
feedback.

Possible strategy:

\[ `\text{Cheap feedback}`{=tex} `\rightarrow`{=tex}
`\text{detect uncertainty/problem}`{=tex} `\rightarrow`{=tex}
`\text{detailed feedback if needed}`{=tex} `\rightarrow`{=tex}
`\text{repair}`{=tex} `\rightarrow`{=tex}
`\text{cheap verification}`{=tex} \]

For example, detailed feedback could be used only when the expected
benefit justifies its cost.

Instead of a fixed rule such as:

> Stop when 90% of tests pass.

a stronger formulation is:

\[ `\text{Stop when}`{=tex} `\quad`{=tex}
`\text{expected value of additional feedback}`{=tex} \<
`\text{cost of additional feedback}`{=tex} \]

A fixed threshold may fail when the remaining test represents a critical
edge case.

------------------------------------------------------------------------

# 13. RLEF Failure Mode: Over-Repair

Execution feedback can produce a loop such as:

``` text
Generate
→ fail
→ patch
→ fail
→ patch
→ fail
→ patch
→ ...
```

The agent may spend its budget reacting to failures rather than
reasoning carefully about:

-   constraints,
-   architecture,
-   edge cases,
-   hidden requirements.

A strong system therefore needs to balance:

\[ `\text{upfront reasoning}`{=tex} \]

with:

\[ `\text{iterative execution feedback}`{=tex} \]

The research question becomes:

> **How should an agent allocate computation between planning/reasoning
> and feedback-driven repair?**

------------------------------------------------------------------------

# 14. Constitutional AI

## 14.1 Motivation

RLHF relies heavily on human feedback.

Humans may need to:

-   inspect responses,
-   compare outputs,
-   provide preferences,
-   write critiques.

This becomes expensive at scale.

Human feedback can also contain:

-   subjectivity,
-   evaluator disagreement,
-   inconsistent application of criteria.

------------------------------------------------------------------------

# 15. Constitutional AI --- Core Idea

Instead of requiring humans to evaluate every individual response,
humans provide a set of **principles**.

The model can then use those principles to critique and revise its own
outputs.

Conceptually:

\[ `\boxed{
\text{Response}
+
\text{Constitution}
\rightarrow
\text{AI Critique}
\rightarrow
\text{Revision}
}`{=tex} \]

The constitution provides the criteria.

The AI supplies the scalable feedback.

This is the core RLAIF idea:

> **Reinforcement Learning from AI Feedback**

------------------------------------------------------------------------

# 16. Constitutional AI Training Pipeline

The lecture describes two major stages.

## Stage 1 --- Critique and Revision / SFT

A response is evaluated according to constitutional principles.

Conceptually:

``` text
Response
   ↓
Critique according to principle
   ↓
Revision
   ↓
Training example
   ↓
SFT
```

The model learns from these generated critique/revision examples.

## Stage 2 --- RL with AI Feedback

A preference/evaluation model is constructed using the constitutional
criteria.

Then RL is used to optimize the model against this AI-generated
feedback.

Conceptually:

\[ `\text{Constitution}`{=tex} `\rightarrow`{=tex}
`\text{AI feedback}`{=tex} `\rightarrow`{=tex}
`\text{Preference model}`{=tex} `\rightarrow`{=tex}
`\text{RL fine-tuning}`{=tex} \]

------------------------------------------------------------------------

# 17. Why RLAIF Scales

Human feedback:

\[ `\text{Output}`{=tex} `\rightarrow`{=tex} `\text{Human}`{=tex}
`\rightarrow`{=tex} `\text{Preference}`{=tex} \]

AI feedback:

\[ `\text{Output}`{=tex} `\rightarrow`{=tex} `\text{AI evaluator}`{=tex}
`\rightarrow`{=tex} `\text{Preference}`{=tex} \]

The second can be executed at much larger scale and in parallel.

This does not eliminate the evaluation problem.

It **moves the problem from human scalability to evaluator
reliability**.

------------------------------------------------------------------------

# 18. AI Evaluator Reliability

Suppose an AI critic is 95% accurate.

That still means approximately 5% of evaluations can be wrong.

The important issue is that these errors can become **training
signals**.

### False positive

Bad behavior:

\[ `\rightarrow`{=tex} `\text{critic incorrectly approves}`{=tex}
`\rightarrow`{=tex} `\text{positive reward}`{=tex} `\rightarrow`{=tex}
`\text{model reinforced}`{=tex} \]

### False negative

Good behavior:

\[ `\rightarrow`{=tex} `\text{critic incorrectly rejects}`{=tex}
`\rightarrow`{=tex} `\text{negative reward}`{=tex} `\rightarrow`{=tex}
`\text{model discouraged}`{=tex} \]

The problem becomes more serious if the evaluator has **systematic
bias**.

Millions of evaluations do not necessarily cancel systematic error.

They can amplify it.

------------------------------------------------------------------------

# 19. Self-Critique and Overconfidence

A model evaluating its own output may share the same weaknesses as the
model that produced the output.

Therefore:

> **Self-critique is not automatically reliable.**

The evaluator can be:

-   overconfident,
-   biased,
-   fooled by plausible reasoning,
-   systematically wrong on certain classes of examples.

This motivates the use of multiple evaluators or external validation.

------------------------------------------------------------------------

# 20. Critic Ensembles

Instead of one evaluator:

\[ C_1(x) \]

we can use several:

\[ C_1(x), C_2(x), C_3(x), `\ldots`{=tex} \]

and aggregate their judgments.

For example:

``` text
Critic A → Good
Critic B → Bad
Critic C → Bad
Critic D → Bad

Majority → Bad
```

Possible aggregation methods include:

-   majority vote,
-   weighted vote,
-   confidence-weighted aggregation,
-   calibrated probabilities,
-   learned aggregation.

### Important distinction

An ensemble of critics is **not necessarily an MoE**.

The critics can remain separate models, with their outputs combined by
an aggregation policy.

------------------------------------------------------------------------

# 21. Critic Diversity

Multiple critics help most when their errors are not perfectly
correlated.

If:

\[ C_A `\approx `{=tex}C_B `\approx `{=tex}C_C \]

then all critics may make the same mistake.

Therefore, an important question is:

> **How diverse are the critics' errors?**

This is more important than simply asking:

> "How many critics do we have?"

------------------------------------------------------------------------

# 22. Helpfulness--Harmlessness Tradeoff

Constitutional AI aims to improve both:

-   helpfulness,
-   harmlessness.

The lecture discusses the helpfulness/harmlessness Pareto frontier and
reports strong results for Constitutional RL with chain-of-thought among
the compared approaches in the cited work.

The broader lesson is that constitutional principles can act as a
scalable specification for AI feedback.

# 24. Feedback as a Research Object

Instead of treating feedback as simply "good" or "bad", analyze it along
several dimensions:

### Informativeness

How much useful information does the feedback provide?

### Reliability

How often is the feedback correct?

### Cost

How expensive is it to obtain?

### Latency

How long does it take?

### Scalability

Can it be generated millions of times?

### Granularity

Does it tell us only whether the final answer is correct, or also
where/why it failed?

### Diversity

Do different feedback sources make independent errors?

------------------------------------------------------------------------

# 25. Adaptive Feedback Selection

A natural research direction from Lecture 4 is to let the agent choose
its feedback source dynamically.

Possible actions:

\[ A = { `\text{think}`{=tex}, `\text{tool call}`{=tex},
`\text{execute}`{=tex}, `\text{AI critic}`{=tex} } \]

The policy chooses based on the current state.

A first intuitive policy:

### Use a tool when:

The agent needs fresh/external factual information.

### Execute when:

The environment provides a mechanical correctness signal.

### Think more when:

The problem requires additional internal reasoning.

### Ask an AI critic when:

The agent is uncertain, stuck, repeatedly encountering the same failure,
or needs another perspective.

------------------------------------------------------------------------

# 26. Formalizing Adaptive Feedback

Let:

\[ s_t \]

be the current state and:

\[ a `\in `{=tex}A \]

be a possible feedback/action choice.

A research objective could be:

\[ a\^\* = `\arg`{=tex}`\max`{=tex}\_a `\frac{
\mathbb{E}[\Delta P(\text{correct}\mid s_t,a)]
}{
C(a)
}`{=tex} \]

In words:

> Choose the action with the highest expected improvement in correctness
> per unit cost.

This captures the central idea:

**Do not ask which feedback method is globally best. Ask which feedback
method is best for the current state.**

------------------------------------------------------------------------

# 27. Example: Smart Contract Agent

Suppose an agent is building a smart contract.

A possible adaptive loop:

``` text
Understand requirements
        ↓
Think / design contract
        ↓
Need current gas information?
        ↓ YES
Tool call
        ↓
Implement
        ↓
Execute tests
        ↓
Tests fail?
   ┌────┴────┐
   YES       NO
    ↓         ↓
Repair      Continue
    ↓
Repeated/similar failures?
    ↓ YES
AI critic
    ↓
New reasoning
    ↓
Execute again
```

The difficult part is deciding where the boundaries lie between:

-   thinking,
-   tool use,
-   execution,
-   critique.

This becomes an **action-selection policy** problem.

------------------------------------------------------------------------

# 28. Research Question

### Adaptive Feedback Selection

> **Can adaptive selection among internal reasoning, external tools,
> execution feedback, and AI critique achieve a better accuracy--cost
> frontier than policies that always use a single feedback source?**

### Hypothesis

An adaptive policy can achieve comparable or better accuracy while using
less inference cost than always using the strongest/most expensive
feedback source.

# 29. Experiment Design

## Baselines

1.  Always think
2.  Always use tools
3.  Always execute when possible
4.  Always use an AI critic
5.  Fixed feedback strategy
6.  Adaptive feedback policy

## Metrics

Measure:

-   final accuracy / solve rate,
-   inference tokens,
-   tool calls,
-   execution calls,
-   critic calls,
-   latency,
-   monetary cost.

## Ablations

Remove one feedback source at a time:

``` text
Adaptive

```

This tells us which components actually matter.

## Failure analysis

Study:

-   wrong action selection,
-   unnecessary tool calls,
-   premature stopping,
-   repeated repair loops,
-   evaluator mistakes,
-   noisy execution feedback,
-   correlated critic errors.

# 30. Important Research Insight

A feedback loop is not automatically useful merely because it contains
feedback.

Its usefulness depends on:

\[ `\boxed{
\text{Feedback quality}
\times
\text{Feedback relevance}
\times
\text{Feedback efficiency}
}`{=tex} \]

A cheap but useless signal is not valuable.

A highly accurate but extremely expensive signal may also be
impractical.

The research objective is therefore often an **accuracy--compute
frontier** rather than maximum accuracy alone.

# 32. Key Terminology

### ReAct

**Reason + Act** --- interleaves reasoning and environment/tool
interaction.

### Observation

Information returned by the environment after an action.

### RLEF

**Reinforcement Learning from Execution Feedback** --- uses execution
outcomes as training/feedback signals for code-generation behavior.

### Execution feedback

Information obtained by actually running generated code.

### Constitutional AI

A framework where AI behavior is guided using human-written principles
and AI-generated critique/revision.

### RLAIF

**Reinforcement Learning from AI Feedback.**

### AI evaluator / critic

A model or evaluation system that judges or critiques another model's
output.

### Feedback granularity

How detailed the feedback signal is, from binary success/failure to
detailed traces or step-level information.

### Feedback policy

A policy deciding which feedback/action to obtain next.

# 34. Research Template From Lecture 4

When analyzing a new feedback-based AI system, ask:

### 1. What is the feedback source?

Environment? Execution? Human? AI critic? Verifier?

### 2. What does the feedback actually measure?

Final correctness? Intermediate progress? Constraint violations?
Preference?

### 3. How reliable is it?

What are the false-positive and false-negative modes?

### 4. How expensive is it?

Tokens, latency, API calls, execution, human labor?

### 5. How granular is it?

Binary outcome or detailed diagnostic information?

### 6. How correlated are errors?

Does an ensemble actually provide independent information?

### 7. When should the agent request feedback?

Always? Periodically? Only under uncertainty?

### 8. What is the baseline?

What would happen with no feedback or a simpler feedback policy?

### 9. What is the hypothesis?

State a falsifiable claim before running the experiment.

### 10. What would falsify the idea?

Define failure conditions in advance.

# 35. Lecture 4 Research Direction

A strong research direction emerging from the lecture is:

> **Adaptive Feedback Selection Under a Fixed Inference Budget**

### Core idea

At each state, an agent chooses between:

\[ { `\text{reason}`{=tex}, `\text{tool}`{=tex}, `\text{execute}`{=tex},
`\text{critic}`{=tex} } \]

based on expected benefit and cost.

### Potential objective

\[ `\max`{=tex} `\frac{\Delta \text{Expected Correctness}}`{=tex}
{`\Delta `{=tex}`\text{Inference Cost}`{=tex}} \]

### Key questions

-   Can uncertainty predict which feedback source is useful?
-   When is execution feedback preferable to AI critique?
-   When should an agent stop reasoning and act?
-   Can feedback granularity be adapted dynamically?
-   Can the system learn its own feedback-selection policy?
-   How much performance is lost when feedback is noisy?
-   Does adaptive feedback improve the accuracy--cost frontier?

This turns Lecture 4 from a collection of papers into a unified research
problem:

\[ `\boxed{
\text{How should an intelligent system decide what information to obtain next?}
}`{=tex}
